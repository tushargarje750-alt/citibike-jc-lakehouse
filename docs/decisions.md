# Design decisions

Short record of choices that shaped the project, and why.

| ID | Decision | Why | Status |
|---|---|---|---|
| D1 | Download source files **inside** the Databricks job (land → bronze → dbt build). | An egress test on 2026-11-14 showed the workspace can reach both the Citi Bike S3 bucket and the Open-Meteo archive API. Keeps the whole pipeline in one scheduled job. Landing code stays plain Python so it can run elsewhere if the Free Edition allowlist changes. | Accepted |
| D2 | Define the job in **Terraform** (Databricks provider) from the start, rather than building it in the UI first. Fallback: Databricks Asset Bundles. | One source of truth for the job; avoids building it twice. Terraform state stays local; CI only runs `fmt` and `validate`. | Accepted |
| D3 | **dbt Core 1.12 + dbt-databricks 1.13**, not dbt v2. | v1 is what the Databricks dbt job task installs by default (`dbt-databricks>=1.0.0,<2.0.0`); v2 only reached general availability in September 2026. | Accepted |
| D4 | Core scope is the **newer trip file format** (`ride_id`, `member_casual`, …). The older format (`tripduration`, `birth year`, …) is a stretch goal. | Two incompatible schemas; the exact switch-over month is verified from file headers in Phase 1. | Accepted |
| D5 | Find files by **listing the bucket and parsing the month with a regex**, never by building URLs. | File names are inconsistent: one has a space, one is misspelled, four omit `.csv` (see metrics log). | Accepted |
| D6 | Secrets only in environment variables: a git-ignored `.env` locally, GitHub Actions secrets in CI. The token variable uses dbt's `DBT_ENV_SECRET_` prefix so dbt masks it in logs. | Public repo; `profiles.yml` can be committed safely. | Accepted |
| D7 | Landing zone keeps each zip **byte-for-byte** (`tripdata/zip/`) and also the extracted CSV in a folder per file format (`tripdata/csv/current/`, `tripdata/csv/legacy/`). | The untouched zip is the audit copy; Auto Loader cannot read zips, and separating formats keeps each bronze stream on one schema. | Accepted |
| D8 | A Delta **manifest table** (one row per source file: ETag, size, SHA-256, header, row count) drives incremental loading. A file is skipped only if its key **and** ETag are unchanged. | Citi Bike republishes old months; comparing ETags catches that. The row counts are control totals for reconciling bronze later. | Accepted |
| D9 | Ingestion logic lives in a plain-Python package (`ingestion/citibike_ingest`) with unit tests; notebooks are thin wrappers. | Testable on a laptop and in CI without a Databricks connection. | Accepted |
| D10 | Bronze trips are loaded with **Auto Loader** (`availableNow` trigger) into an append-only Delta table: every source column as text, plus six metadata columns, liquid-clustered by source month. | Auto Loader's checkpoint gives exactly-once, file-level incremental loads without custom bookkeeping. Keeping text avoids losing rows to type errors before silver can quarantine them. | Accepted |
| D11 | After each bronze load, **row counts per month are reconciled** against the landing manifest; any mismatch fails the run. | A control total catches dropped or duplicated rows at the earliest point. | Accepted |
| D12 | Bronze weather is rebuilt in full on every run (one row per day, values and units untouched). | About 4,000 rows; a full rebuild is simpler and always consistent with the landed files. | Accepted |
| D13 | Silver applies **named rejection rules** in a fixed order (missing id, unparseable time, non-positive duration, under 60 s, over 24 h, no start station, invalid rider type, start outside the service area, duplicate ride_id). Rejected rows go to `trips_quarantine` with the reason; nothing is dropped silently. | A singular test proves bronze rows = accepted + quarantined, so every row is accounted for. Thresholds are dbt vars, not hard-coded SQL. The 60-second floor follows Citi Bike's own published rule for false starts. | Accepted |
| D14 | `fct_trips` is an **incremental merge on ride_id**: each run processes only bronze rows loaded since the last run. | Monthly files are append-mostly; a ride that arrives again replaces its earlier row instead of duplicating it. | Accepted |
| D15 | Schema names are used as written (`citibike_silver`, `citibike_gold`), with an optional prefix from `DBT_SCHEMA_PREFIX`. | CI can build into `ci_…` schemas without touching the real tables. | Accepted |
| D16 | **No third-party dbt packages**; the range test is written in the project (`tests/generic/value_between.sql`). | The scheduled job runs on Free Edition compute with restricted internet access, so `dbt deps` downloads could fail there. | Accepted |
| D17 | Gold is six small aggregate tables, rebuilt in full each run, each tested to **add up to `fct_trips`**. | Aggregates over about 5 million rows rebuild in seconds; a reconciliation test guards against join fan-out or dropped groups. | Accepted |
| D18 | Weather impact is measured with a **ridership index**: each day's trips divided by the average day of the same month. | The system grew every year, so raw daily counts would mostly compare early years with late years rather than wet days with dry days. | Accepted |
| D19 | Trip-length percentiles are computed on whole seconds and converted to minutes afterwards. | Local testing on Spark 4.0 showed that an approximate percentile of the rounded decimal column, rounded again, silently returned NULL. Not-null tests now guard those columns. | Accepted |
| D20 | dbt docs are generated and viewed locally for now; publishing to GitHub Pages moves to the CI phase. | The docs build needs a warehouse connection, which CI will have. | Accepted |
| D21 | One Databricks job with five tasks (two landing, two bronze, one `dbt build`); trips and weather run in parallel and meet at dbt. All tasks use **serverless** compute. | Free Edition only offers serverless; the fan-in keeps dbt from starting until both bronze tables are current. | Accepted |
| D22 | The job **checks out the code from GitHub `main`** on every run (`git_source`), instead of pointing at notebooks in a workspace folder. | What runs in production is exactly what was reviewed and merged; no manual "pull" step. | Accepted |
| D23 | Terraform authenticates with the **Databricks CLI profile**; state is local and git-ignored; the warehouse is looked up by name. | No host, token or resource ID is committed to a public repo. | Accepted |
| D24 | The schedule is **weekly** (Mondays 06:00 New York time). | Trip files are published monthly; a weekly run picks them up within days and stays well inside the Free Edition daily compute quota. | Accepted |
| D25 | CI runs three independent checks on every push and pull request: Python unit tests, Terraform `fmt` + `validate`, and a real `dbt build` against Databricks. | Each catches a different class of mistake; the first two need no credentials and finish in seconds. | Accepted |
| D26 | The CI dbt build reads **one month** of bronze (`only_source_month` var) and writes to **`ci_`-prefixed schemas** with `--full-refresh`; CI runs are serialised. | Proves the whole project builds and all tests pass from scratch in about a minute, without touching production tables or the Free Edition quota. | Accepted |
| D27 | dbt docs are published to GitHub Pages by a separate workflow; table owners are stripped from the catalog first. | The site is public and Unity Catalog owners are account email addresses. A separate workflow keeps a Pages problem from failing CI. | Accepted |
| D28 | CI uses its **own access token**, stored as a GitHub Actions secret. | It can be revoked or rotated without breaking local development, and never appears in the repo or logs (dbt masks `DBT_ENV_SECRET_` values). | Accepted |
